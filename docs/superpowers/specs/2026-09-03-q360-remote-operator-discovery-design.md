# Q360 远程操作者状态发现设计

## 文档状态

- 日期：2026-09-03。
- 状态：远程操作设计已确认；传输窗口与时限按后续规格修订，等待 `0.2.2` 本地验证。
- 适用版本：当前修订计划发布为 `0.2.2`。
- 与现有规格的关系：本规格是
  [Q360 面板状态发现 v2 设计](./2026-09-03-q360-panel-state-discovery-v2-design.md)
  的操作安全补充。它只取代其中“操作者必须位于实体面板旁”的真实实验要求；v2 的协议、
  状态机、Action 参数、实验目录、报告 schema、Store key 和隐私边界保持不变。传输准备和超时
  由 [Q360 发现传输窗口与远程超时修复设计](./2026-09-03-q360-discovery-transport-window-design.md)
  修订。

## 背景

v2 已经实现并部署。当前真实实验手册要求操作者站在实体面板旁，但实际实验操作者不在设备
现场，可以同时使用手机上的奥普官方 App 或官方微信小程序、电脑上的 Home Assistant 和聊天。
官方控制面能够显示并操作七个独立模式、全局档位 `1..5` 和 AI 温度 `30..42°C`。家中另有
人员，可以在异常时现场检查、关闭设备或按既有安全方式断电。

因此，真实发现可以改为“远程控制面操作、现场人员应急兜底”。这个变化不能把官方控制面
接入集成，也不能降低 Shadow `reported` 的证据标准。

## 目标

1. 允许操作者通过奥普官方 App 或官方微信小程序完成 v2 单变量实验。
2. 保留一条独立的现场安全兜底路径，异常或恢复不确定时必须由家中人员最终确认。
3. 明确区分“操作确认”和“字段证据”：官方控制面只确认人工操作流程，字段语义仍只认目标
   设备 Shadow `reported`。
4. 更新 HA Action 提示、中文翻译和运行文档，使其适用于实体面板或官方远程控制面。
5. 保持 discovery 观察只读，不增加控制 API、自动化控制或新的敏感材料。

## 非目标

- 不调用、逆向或自动化奥普官方 App、微信小程序及其私有控制接口。
- 不让 Home Assistant 替操作者控制模式、档位或温度。
- 不把官方控制面显示、用户陈述、Action 阶段或 Shadow `desired` 当作字段证据。
- 不改变五个 discovery Actions 的名称、参数、响应结构或状态转移。
- 不改变固定实验目录、取值范围、其余资源限制、v2 Store key 或报告 schema。
- 不创建正式模式、档位或温度实体，不承诺任何未知字段映射。
- 不读取、显示、上传或提交原始 topic、payload、凭据、Token、Cookie 或档案内容。
- 不修改 Compose、私有档案根目录或现有 HA 部署拓扑。

## 方案选择

### 采用：官方远程控制面加现场应急兜底

把原规格中的“实体面板”抽象为“操作者控制面”。操作者可使用实体面板、奥普官方 App 或官方
微信小程序手工完成提示动作；集成仍只发送关联 Shadow `get`。正常远程流程不要求现场人员
逐步骤观察，但现场人员在整个会话期间必须可联系，并在异常时接管安全恢复。

这个方案不改变现有技术接口，能够直接复用 v2 的单变量实验和 `reported` 证据链。

### 未采用：只改运行手册

仅修改文档会让 HA Action 继续提示“实体面板”，在超时或恢复失败时也不会呈现远程现场兜底
要求，容易造成操作歧义。

### 未采用：给 Action 增加控制面类型

新增 `operator_surface` 等参数会改变公共接口和状态机输入，却不会增强 Shadow 证据。控制面
类型只影响人工操作说明，不应进入报告或发现模型。

## 架构与证据流

真实会话包含两条严格分离的链路：

```text
人工控制链：手机官方控制面 ──> 奥普官方云 ──> Q360

观察证据链：HA discovery Action ──> 关联 Shadow get
                                      └─> 目标 get/accepted reported
                                           └─> 阶段差异与 schema 2 脱敏报告
```

官方控制面不由集成调用，也不向 discovery 提供数据。刷新或重开官方控制面只用于确认操作者
刚执行的控制动作和安全恢复，没有资格确认字段路径、字段值或设备侧执行结果。

start 会先续建 WSS，并在确认新连接 healthy 后才建立发现基线，随后沿用同一 observer 边界。
正式照明解析继续优先于 discovery observer；observer 失败不能影响照明状态或 WSS 重连。
discovery 网络守卫继续禁止 Shadow `update`、`desired`、设备控制 HTTP API 以及任何官方控制面
私有接口。

## 术语与 Action 语义

“操作者控制面”指以下任一人工界面：

- Q360 实体面板；
- 奥普官方 App；
- 奥普官方微信小程序。

一次远程会话使用手机上的一个官方控制面，不在正常阶段中途切换。控制面失联或状态不一致时
中止会话，不以切换界面的方式继续收集。

`all_modes_off_confirmed=true` 保持原参数名和类型。远程会话中，它表示操作者已经在官方控制面
关闭七个模式，并在刷新或重开页面后确认它们仍显示为关闭。这个布尔值是开始实验的人工安全
声明，不是 `reported` 证据。

所有固定 `message_code`、Action 响应 schema 和错误码保持不变。英文源字符串和简体中文翻译
只调整人类可读说明：正常提示使用“操作者控制面”，异常提示明确要求停止采集并安排现场确认。

## 远程会话前提

开始真实会话前必须同时满足：

1. 操作者预留连续 45–60 分钟，并保持手机、电脑 HA 和聊天在线。
2. 浴室无人、无宠物、设备没有被衣物或其他物品覆盖，适合短时远程启动暖风和干燥模式。
3. 家中人员已知设备位置、实体停止方式和既有安全断电方式，整个会话期间保持可联系。
4. 会话期间没有其他人操作 Q360；可能控制 Q360 的自动化已暂停。
5. HA 运行版本、组件哈希、固定私有挂载、connectivity、WSS connected/healthy 和现有灯光状态
   均通过只读复核；AUPU 相关错误日志为空。
6. 操作者在官方控制面私下记录原始全局档位和原始 AI 温度，不把值写入聊天或普通日志。
7. 操作者关闭七个模式，刷新或重开官方控制面，并确认七个模式仍显示关闭。
8. 若本次需要原始档案，只在真实实验授权后启用 Options；Options reload 不得自动开始发现。

任何前提不成立都不得调用 `aupu_q360.start_discovery`。

## 正常远程实验流程

### 启动

在电脑的 HA“开发者工具 → 操作”中选择目标 Config Entry，调用
`aupu_q360.start_discovery`，并设置 `all_modes_off_confirmed: true`。只有返回
`discovery_ready_for_step` 才能继续；其他响应或十秒快照超时进入异常流程。
WSS 准备最多等待 45 秒；每个等待操作者的阶段最多 300 秒，完整发现会话最多 3,300 秒。旧 v2
报告中的 120/3,600 超时 profile 只用于读取兼容，不是当前运行时限。

### 固定操作规则

- 严格按现有目录完成两轮静置、七种模式各两轮、其余四个全局档位各两轮，以及同一个相邻
  AI 温度两轮。
- 每次 `begin_discovery_step` 后只执行当前固定提示要求的一个手机操作。
- 操作后刷新官方控制面，确认它显示刚请求的状态，等待 15–30 秒，再调用
  `advance_discovery_step`。
- 一个阶段不得同时改变其他模式、全局档位或 AI 温度，也不得由其他人或自动化控制设备。
- 官方控制面显示只决定人工流程能否继续；阶段是否取得证据仍由关联 Shadow
  `get/accepted` 的 `reported` 快照决定。
- 只有收到 `discovery_cycle_recorded` 才能开始下一轮。

### 固定顺序

1. `idle_environment` round 1 和 round 2，期间不操作设备。
2. 七个模式各完成两轮开启和关闭；每个恢复阶段在官方控制面关闭该模式并刷新确认。
3. 以换气为载体，把原始全局档位分别改到其他四档，每档两轮；每轮恢复原档位并关闭换气。
4. 以 AI 恒温暖为载体，把原始温度改到固定相邻温度，两轮使用同一方向；每轮恢复原温度并
   关闭 AI 恒温暖。
5. 会话回到 ready 且没有待恢复阶段后，调用 `aupu_q360.finish_discovery`。

### 正常完成

完成后再次在官方控制面确认七个模式全关、原始全局档位和原始 AI 温度均已恢复。正常完成不
强制现场人员逐项复核。随后只检查 schema 2 脱敏报告以及档案的权限、状态、事件数、编码字节数
和 SHA-256；不得打开、打印或分享原始档案内容。

## 异常停止与现场兜底

以下任一情况触发异常流程：

- Action 没有返回当前阶段允许的结果；
- 收到 `discovery_restore_required` 或 `discovery_manual_restore_required`；
- 快照、阶段或会话超时；
- WSS 断开或不健康，或者发生鉴权、档案、资源限制或 payload 校验错误；
- 官方控制面无法刷新、显示与刚执行的操作不一致或控制失败；
- 手机、HA 或聊天中的必要链路失联；
- 家中人员报告异常声音、气味、热量或其他非预期行为；
- 无法确定模式、档位或温度是否恢复。

远程运行手册采用比状态机更严格的恢复规则：状态机仍保留对
`discovery_restore_required` 的同阶段重试能力，但远程会话不得利用该能力继续实验。该响应表示
`reported` 尚未确认恢复，必须按恢复不确定处理。

异常处理顺序固定为：

1. 立即停止手机上的进一步实验操作，不开始新阶段。
2. HA 仍可用时调用 `aupu_q360.cancel_discovery`。取消只停止采集，不控制或恢复设备。
3. 当前载体仍开启时，先在官方控制面恢复原档位或原温度，再关闭全部模式，然后刷新或重开
   页面。
4. 载体已经关闭、官方控制面状态不确定，或恢复需要重新开启模式时，不再远程尝试，由现场人员
   接管。
5. 无论官方控制面显示什么，都通知家中人员现场确认设备已停止发热、送风及其他运行。
6. 官方控制面无法控制、现场状态不明确或设备仍异常时，由现场人员使用实体控制面停止设备；
   仍无法恢复时，按家中既有安全方式切断该设备供电。
7. 只记录固定错误码、阶段和明确时间戳。保留标记为 incomplete 的私有档案，不读取、不输出、
   不删除其内容。
8. 不自动重试或接着原会话继续。再次实验必须重新完成全部预检并重新取得真实设备实验授权。

HA 已失联时无法调用 `cancel_discovery`，但这不影响人工安全恢复的优先级。操作者停止继续实验，
只有当前载体仍开启且官方控制面状态明确时才按上述顺序远程恢复，否则直接通知现场人员接管；
软件侧由既有时限和连接清理机制收敛，恢复 HA 后再做只读核查。

## 测试策略

实施采用测试先行：

1. 先让契约测试要求 README、运行手册和翻译包含官方远程控制面、`reported` 唯一证据及异常现场
   兜底规则，并拒绝旧的“操作者必须在实体面板旁”正常流程。
2. 保持五个 Actions、字段矩阵、固定 message codes 和中英文 key tree 完全一致。
3. 将四处版本来源、lock file 和版本断言统一为 `0.2.2`。
4. 保持网络边界测试，证明 discovery 只依赖 `async_request_shadow_get`，没有控制 API、Shadow
   `update`/`desired` 或官方控制面接口。
5. 运行完整 pytest、HA runtime 测试、Ruff、格式检查、mypy、私有签名检查、敏感信息扫描和
   `git diff --check`。

所有测试只使用合成数据和本地 HA runtime；测试通过不证明真实字段语义，也不授权真实设备操作。

## 提交、重新部署与真实实验边界

以下步骤继续相互独立，前一步完成不自动授权后一步：

1. 审查并提交规格与本地实现；
2. 推送 `0.2.2`；
3. 将已验证组件同步到实际 HA `/config/custom_components`；
4. 重启实际 Home Assistant，使新版本和提示生效；本变更不需要修改 Compose 或重建容器；
5. 做无 discovery 烟测，确认 HA 版本、Config Entry、照明、connectivity、WSS 和错误日志；
6. 单独授权启用私有原始档案 Options 和执行真实远程会话。

每个对外写入或运行态步骤执行前都要重新检查当前状态，并取得对应明确授权。

## 完成标准

1. 正常操作文档和 HA 提示同时支持实体面板与奥普官方远程控制面。
2. 文档明确官方控制面显示不是字段证据，候选仍只由 Shadow `reported` 产生。
3. 远程预检覆盖环境、在线链路、自动化隔离、原始值记录和全部模式关闭。
4. 异常、超时、断线、恢复不确定或控制面状态不一致时停止会话，并强制现场最终确认。
5. Action 参数、状态机、实验目录、Store key、报告 schema、档案边界和网络只读性没有变化。
6. 版本为 `0.2.2`，所有本地与 HA runtime 验证通过。
7. 重新部署后的无 discovery 烟测通过，且没有提前启用档案、创建会话或操作真实设备。

真实远程会话只有在新的独立授权下才能开始。实验完成仍只产生字段候选；任何正式实体或控制
能力都需要新的规格、测试、提交、部署和真实验证。
