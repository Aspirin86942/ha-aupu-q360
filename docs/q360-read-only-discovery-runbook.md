# Q360 临时状态探针运行手册

本手册用于通过现有 AWS IoT WSS 一次性观察 Q360 Shadow `reported` 的安全标量变化。探针是
临时开发工具，不是正式功能；它不控制设备、不解释实验含义、不猜测未知字段，也不保存任何
快照、差异或报告。

现有 WSS 解析器已经能看到解密后的 Shadow JSON，所以外部 HAR/PCAP 不是默认前提。只有目标
设备、匹配 token 的 `get/accepted` 中的 `state.reported` 可以完成一次快照；官方控制面显示、
`desired`、用户陈述和未关联消息都不能确认字段语义。

## Action 与数据边界

三个 Action 都只接受 `config_entry_id`：

- `aupu_q360.start_probe`：续建现有 WSS，取得一份关联基线并保存在内存中；
- `aupu_q360.sample_probe`：取得下一份关联快照，返回它与上一份快照的差异并替换内存基线；
- `aupu_q360.stop_probe`：只清理探针内存和观察器，不恢复或控制设备。

响应只包含规范化 `service/<n>/property/<n>` 路径、布尔值、`-1000..1000` 整数、样本计数和固定
消息码。探针不保存 device id、token、topic、payload、快照或差异，不写入 Config Entry、HA
Store、Diagnostics、文件或日志。断线、超时、无效 payload、Config Entry unload、HA stop 和
显式停止都会清空内存。

## 本地实施验证

在隔离的 Linux checkout 中运行：

```bash
uv sync --locked
uv lock --check
uv run pytest -q
AUPU_RUN_HA_RUNTIME=1 uv run --group ha-test pytest tests/ha_runtime -m ha_runtime -v
uv run ruff check .
uv run ruff format --check .
uv run mypy custom_components/aupu_q360
uv run python scripts/verify_private_signer.py
uv run python scripts/check_no_secrets.py
git diff --check
```

测试只使用合成路径和内存 WSS。通过测试不证明任何真实字段语义，也不授权部署、重启、真实
设备实验、推送或发布。

## 独立运行范围

本地实现完成后，以下范围仍需分别取得明确授权：

1. 临时部署：重新核实源与 HA runtime 路径，备份并同步组件，检查配置并只重启实际 HA 容器；
2. 手机实验：重新核实 WSS、现场安全和自动化暂停状态后，调用探针 Action；用户只操作官方
   手机控制面；
3. 正式映射与最终清理：真实证据形成独立规格后实现正式字段，并删除临时探针再部署。

临时部署不修改 Compose，不读取凭据，不创建原始档案目录，不开始探针，不推送也不发布。

## 手机实验前检查

只有取得真实设备范围的当前授权，并同时满足以下条件时才继续：

- 浴室无人、无宠物、设备无遮挡，家中安全联系人可随时接管；
- 可能控制 Q360 的自动化已暂停，其他人不会同时操作设备；
- WSS connected/healthy，正式照明与 connectivity 语义正常；
- 探针处于 inactive，AUPU 相关错误日志为空；
- 用户私下记住原始档位和原始温度，不在聊天或日志中输出；
- 官方控制面上的模式、档位和温度已处于安全、可恢复状态。

这些前提只允许开始观察，不允许软件控制设备。任何前提不成立都不得调用
`aupu_q360.start_probe`。

## 自适应采样流程

所有设备变化都由用户在奥普官方 App 或官方微信小程序中手工完成；每次只改变一个变量。
操作者完成一次变化后，代理才调用一次 `aupu_q360.sample_probe`。

1. 调用 `aupu_q360.start_probe` 建立基线；不操作手机，调用一次 `sample_probe` 记录背景变化。
2. 七个模式逐个执行“开启、sample、关闭、sample”，每个模式都必须看到变化与恢复。
3. 以换气为载体：开启并 sample，改到一个非原档并 sample，恢复原档并 sample，关闭并
   sample。只有结果不唯一时才选择第二个目标档复核。
4. 以 AI 恒温暖为载体：开启并 sample，修改一个合法目标温度并 sample，恢复原温度并
   sample，关闭并 sample。只有结果不唯一时才选择第二个温度复核。
5. 调用 `aupu_q360.stop_probe`，再由用户在官方控制面确认模式、档位和温度已恢复。

基准流程约 23 次 `sample_probe`，不是固定重复两轮的完整矩阵。背景样本出现的路径不能直接
确认；每项候选都必须同时具备单变量变化和恢复证据。

## 空白或模糊结果

探针只保留布尔值和小整数，因此并非所有能力一定可见。某项能力连续两次单变量操作都返回空
差异，或连续两次仍只得到无法由变化/恢复配对排除的多个路径时：

1. 把该能力标记为“Shadow 探针不可确认”；
2. 停止该能力的远程尝试，不猜测路径或值域；
3. 不把外部 TLS 抓包当作解密后应用层证据；
4. 另行编写并授权奥普 App 层短期观察方案。

这条降级规则只针对未确认能力，不要求已经得到唯一变化/恢复证据的能力无条件重做。

## 异常停止与恢复

出现 WSS 断开或不健康、鉴权失败、快照超时、无效 payload、官方控制面失联、设备行为异常、
无法确认恢复或任何非预期响应时：

1. 立即停止继续操作；
2. HA 可用时调用 `aupu_q360.stop_probe`，它只清理软件内存；
3. 若当前载体仍明确开启，由用户先恢复原档位或原温度，再关闭模式；
4. 状态不明确、恢复需要重新开启模式或远程控制不可靠时，不再远程尝试，由家中人员现场接管；
5. 家中人员确认设备已停止发热、送风及其他运行，必要时使用家中既有安全断电方式；
6. 恢复 HA 后只做只读核查；再次实验必须重新预检并重新取得授权。

探针不会替用户恢复设备，也没有后台重试、阶段状态机或“最后报告”。

## 实验输出与后续计划

当前受控会话只记录 Action 响应中的规范路径、允许值变化、恢复证据和未确认能力，不复制
device id、token、原始 topic/payload 或官方控制面私有材料。探针本身不生成证据文件。

只有获得可复核的真实路径、类型、值域和恢复证据后，才能另写正式映射规格与实施计划。后续
计划必须删除 `probe.py`、三个 probe Action、翻译、运行手册和专项测试；证据不足时缩小正式
映射范围，不能把临时探针保留为默认长期功能。
